# CEO Account Takeover Investigation — Microsoft Sentinel Lab

**Role simulated:** SOC Analyst
**Tools:** Microsoft Sentinel, Microsoft Entra ID, KQL
**Type:** Self-directed detection engineering lab (see note on scope below)

## Overview

This project simulates and investigates a Business Email Compromise (BEC)-style account takeover scenario against a company's CEO account. A self-built Microsoft Sentinel lab was used to generate, detect, and investigate a realistic attack chain: a password spray against multiple accounts, followed by a successful takeover of a high-value ("CEO") account, followed by persistence actions (password change and MFA device registration) consistent with real-world BEC attacker behavior.

All data in this repository is real telemetry generated by the author inside an isolated Azure/Entra ID lab tenant. No production systems, real employees, or real incidents are represented.

**Scope note:** This is a self-directed lab built to demonstrate SOC analyst skills for a job search portfolio. It is not a report of an actual security incident at any organization. One planned stage (an inbox rule / invoice-fraud persistence mechanism) was not completed live due to Exchange Online mailbox licensing limits on the free-tier lab tenant; this is documented in Stage 4 below with the detection logic that would apply in a fully licensed environment.

## Attack Simulation

To generate realistic log data, the following activity was performed against test accounts in the lab tenant:

1. **Password spray:** Repeated failed sign-in attempts (incorrect passwords) against three standard user test accounts, mimicking a credential-guessing attack against multiple employees.
2. **Account takeover:** A successful sign-in to the CEO test account using its correct (rotated) credentials.
3. **Persistence:** A mandatory password change on first sign-in, followed by registration of a new MFA method (Microsoft Authenticator) on the CEO account — mirroring how an attacker locks in persistent access after an initial compromise.

## Investigation

### Stage 1 — Triage the Alert

**Scenario:** A sign-in to the CEO's account is flagged for review.

**What we do:**
- Open Microsoft Sentinel and confirm the workspace is receiving Entra ID sign-in data
- Pull sign-in logs for the CEO account
- Validate whether the sign-in is expected or anomalous

**Goal:** Confirm whether this is a true anomaly that needs investigation.

---

### Stage 2 — Hunt Backwards: How Did They Get In?

**Scenario:** Before confirming the CEO sign-in as malicious, we look for evidence of how access may have been obtained — starting with a check for credential-guessing activity across the tenant.

**KQL query:**

```kql
SigninLogs
| where TimeGenerated > ago(24h)
| where ResultType == "50126"
| summarize FailedAttempts = count() by UserPrincipalName, IPAddress, bin(TimeGenerated, 1h)
| where FailedAttempts > 3
| order by FailedAttempts desc
```

**Result:** Three accounts (`jsmith`, `ksam`, `kbold`) show 8–9 failed sign-in attempts each, all from the same source IP, within the same one-hour window — a clear password spray signature.

*Screenshot: `screenshots/03-password-spray-detection.png`*

**Goal:** Identify the attacker's entry point and confirm the pattern is consistent with credential spraying rather than isolated user error.

---

### Stage 3 — Correlate: Confirming the Takeover

**Scenario:** With the password spray confirmed, we check whether it was followed by a successful sign-in to a high-value account.

**KQL query:**

```kql
SigninLogs
| where TimeGenerated > ago(24h)
| where UserPrincipalName == "ceo-test@rainyoung89gmail.onmicrosoft.com"
| where ResultType == "0"
| project TimeGenerated, UserPrincipalName, IPAddress, Location, ResultType
| order by TimeGenerated desc
```

**Result:** Two successful sign-ins (`ResultType == 0`) to the CEO account, both occurring after the password spray activity against the other three accounts.

*Screenshot: `screenshots/04-ceo-successful-signin.png`*

**Goal:** Establish a timeline linking the spray activity to the successful compromise of the target account.

---

### Stage 4 — Check Persistence & Malicious Actions

**Scenario:** Attackers rarely stop at initial access. We check Entra ID Audit Logs for account-management activity that would let an attacker maintain access after the initial takeover.

**KQL query:**

```kql
AuditLogs
| where TimeGenerated > ago(24h)
| where TargetResources has "ceo-test@rainyoung89gmail.onmicrosoft.com" or InitiatedBy has "ceo-test@rainyoung89gmail.onmicrosoft.com"
| project TimeGenerated, OperationName, InitiatedBy, Result
| order by TimeGenerated desc
```

**Result:** 22 audit events on the CEO account, including:
- `Change password (self-service)` — the mandatory password reset on first sign-in
- `User started security info registration`
- `User registered security info` and `POST UserAuthMethod.SoftwareOathProofupRegistration` — a new MFA method (Microsoft Authenticator) registered on the account

*Screenshot: `screenshots/05-persistence-audit-log.png`*

**Goal:** Confirm whether the attacker (or in this simulation, the test operator standing in as one) established persistence beyond the initial sign-in.

**Note on inbox rule persistence (not completed live):** A common real-world BEC persistence technique is a hidden inbox rule (e.g., auto-forwarding or auto-deleting emails containing "invoice") used to intercept finance communications. This lab's Entra ID Free tier does not include an Exchange Online mailbox, so this step could not be generated live. In a licensed environment, this activity would appear in Exchange audit logs and could be hunted with a query such as:

```kql
OfficeActivity
| where TimeGenerated > ago(24h)
| where Operation == "New-InboxRule" or Operation == "Set-InboxRule"
| project TimeGenerated, UserId, Operation, Parameters
| order by TimeGenerated desc
```

## Findings & Remediation (Simulated Response)

If this had been a real incident, recommended containment and remediation steps would include:

1. Disable the compromised account and revoke all active sessions/tokens
2. Force a password reset through an out-of-band channel (not email)
3. Remove any unauthorized MFA methods registered during the compromise window
4. Review and remove any unauthorized inbox rules or mailbox delegations
5. Block the source IP(s) associated with the password spray at the network/conditional access layer
6. Enable/enforce Conditional Access policies (MFA-required, risky sign-in blocking) tenant-wide
7. Notify affected users and reset credentials for any other accounts targeted in the spray
